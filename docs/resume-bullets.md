## 一、简历项目经历（可直接改写）

> **DataPilot — 基于 MCP + LangGraph 的中文 ChatBI 数据分析助手**（个人项目，GitHub 开源）
> 自然语言问答式数据分析系统：中文问题 → 自动选表选列 → 生成并自修复 SQL → 执行 → 输出图表与结论；
> 技术栈：LangGraph、MCP、GLM-4-Flash、DuckDB、BM25+BGE-M3 混合检索、QLoRA。

**个人工作（技术决策 + 量化结果）**
- 设计"Workflow 主干 + 局部 Agent 回环"架构：SQL 生成走固定五阶段流水线（可控、可测），仅在【校验/执行】失败时把控制权交还 LLM 自修复（≤3 轮，错误信息回填重生成），自修复将预测 SQL 可执行率从【a%】提升至【b%】；
- 实现两处非常规 RAG：Schema Linking（BM25+向量双路召回、RRF 融合，将候选表列从 N 个压缩到 3 表级 mini schema）使 SQL 执行准确率（EX）提升【x pp】、平均 Token 下降【y%】；相似问-SQL Few-shot 检索对齐 JOIN 惯例，多表题 EX 提升【z pp】；
- 将数据库能力封装为 5 个标准 MCP 工具（FastMCP），单一实现同时支持进程内直调与 stdio server 接入，任何 MCP 客户端可直接复用工具集；
- 使用 QLoRA（NF4 + LoRA r=16）微调 Qwen2.5-Coder-3B，按库划分防数据泄漏，CSpider dev 上 EX 从【u】提升至【v】，接近未微调 7B API 模型（【w】）而单查询 Token 成本降低约【n】倍。

**项目难点（问题 → 方案 → 效果，挑 2 条最熟的写）**
- 难点 1：LLM 生成的 SQL 约【a%】存在列名/聚合错误。→ 用 `EXPLAIN` 预检代替真实执行来发现错误（无副作用、快），错误信息回填触发修复回环；区分"语法错误"与"语义错误"分别给提示。→ 可执行率【…】。
- 难点 2：schema linking 在小表库上召回好，但跨 3 表以上的复杂问题会漏表。→ 表文档与列文档双粒度建索引、列命中按 0.5 权重折算回表分，表级 recall@3 达【…】；仍漏表时降级为全量 schema 并在报告中标注置信度。

**个人收获**
- 建立了对"什么时候该用 Workflow、什么时候交还给 Agent"的判断标准：主干要可控可测，灵活性只花在失败恢复上；
- 掌握了从"能跑通"到"可评估"的差距：没有 EX、召回率、修复率这些指标，所有优化都是感觉。

## 三、面试追问预案（每个问题都从项目真实设计出发）

**Q1: Agent 和 Workflow 的区别？你为什么这么设计？**
A: Workflow 控制流写死在代码里，Agent 把控制流交给 LLM 动态决策。我的取舍是主干用 Workflow——五阶段固定、每阶段可单测可计时；只在"SQL 校验/执行失败"这一个分支点把控制权交给 LLM 自修复。原因是 Text-to-SQL 的主路径高度可预测，全 Agent 化只会多花 4-8 倍 Token 换不来质量；而失败恢复的搜索空间（改列名/改聚合/改 JOIN）不可枚举，交给 LLM 划算。量化：全 Agent 方案 vs 我的混合方案，Token 差约【…】倍，EX 差距在【…】以内。

**Q2: MCP 解决什么问题？和直接写 Function Calling 有什么区别？**
A: Function Calling 是"模型和我的代码之间"的约定，每接一个新宿主都要重新写 adapter；MCP 把工具实现和宿主解耦，工具方实现一次 server，任何 MCP 客户端都能发现并调用。我的项目里同一套 ToolCore 既被 LangGraph 进程内直调（低延迟），也被 FastMCP 包成 stdio server 供外部客户端复用——工具逻辑零拷贝。

**Q3: 你的 RAG 为什么检索的不是文档？和常规 RAG 有什么区别？**
A: ChatBI 里的 RAG 检索对象是 schema 元数据和"相似问-SQL 对"。前者解决上下文窗口问题（上百字段塞不进还诱发幻觉），后者解决风格对齐问题（JOIN 惯例、别名、LIMIT 习惯）。评估方式也不同：文档 RAG 评忠实度，这里评表级 recall@k 和 EX 增益。

**Q4: 为什么用混合检索而不是纯向量？**
A: 表名、字段名、业务词（"退款"→ status='已退款'）是强精确匹配信号，BM25 对术语命中极敏感；向量负责同义改写（"营业额"→ 收入/amount）。两路召回用 RRF 融合，不需要调权重尺度。我做过的对比：【数据规模】下纯 BM25 / 纯向量 / RRF 的 recall@3 分别是【…】。

**Q5: Text-to-SQL 怎么防注入/防写库？**
A: 三层：语句级（只允许单条 SELECT/WITH）、关键字级（词边界正则拦截 INSERT/DROP/ATTACH/COPY 等）、行为级（连接层只读，`EXPLAIN` 预检）。注意不能用简单的子串匹配——注释和字符串字面量里出现关键字会造成误拦/漏拦，我统一在剥离注释后做词边界校验。

**Q6: 微调的数据怎么构造？怎么防止过拟合/泄漏？**
A: CSpider train 转 ChatBI 对话格式，关键是"训练时看到的 schema 表述方式与线上推理一致"（否则分布漂移）；按 db_id 划分 train/val（同库样本绝不跨集）；过滤含写操作/超长的样本。评测在 dev 上跑 EX 而不是看训练 loss。

**Q7: 什么时候该 RAG、什么时候该微调？**
A: 知识频繁变化/需要溯源 → RAG；输出风格、格式、领域惯例需要固化、且能承受一次训练成本 → 微调。我的项目两者都用了：RAG 管信息注入，微调管 SQL 方言风格的固化，二者正交。

**Q8: 如果查询结果是空的，怎么判断是"数据为空"还是"查错了"？**
A: 这是 Roadmap 里的幻觉归因问题（诚实回答思路）：先看 linking 是否命中了 gold 常用表 → 用一个轻量 LLM 校验步骤对 SQL 做语义审查 → 降级回复中说明置信度，不编造结论。
